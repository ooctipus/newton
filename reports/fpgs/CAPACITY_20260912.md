## FPGS: missing rows were real

Keyboard's old 192-row dense allocation could see **615 requested rows** and
drop **423**. These are mostly three-row frictional contacts, not duplicated
keyboard position limits. The 108 independent keyboard key limits use the
existing fused path outside this allocator.

The implementation now latches dense, matrix-free, propagation, and incoming
contact-capacity failures independently of opt-in detailed telemetry. Four
int32 flags survive successful/empty steps and CUDA graph replays. They add no
new per-step kernel or host synchronization. `constraint_capacity_status()`
reads them; `check_constraint_capacity()` raises. Call at safe host observation
boundaries on the correct/joined stream. Explicit clearing acknowledges an
earlier failure; it cannot repair lost work. This is not automatic graph abort.

This API does **not** cover every upstream collision queue or the separate
matrix-free unique-body cap. Internal collision demand must be calibrated
separately; an upstream lost pair cannot be recovered by a solver row check.

Regression-first tests include 205 sphere-plane contacts: 640- and 768-row
solutions agree within FP32 tolerance and satisfy physical checks; 192 rows
omit a necessary contact and change motion. All 28 focused tests passed on
both GPUs, including sticky status during repeated graph replay. Three broader
CPU-path failures were reproduced on the clean starting revision and are not
claimed fixed by this change.

### Keyboard, 4,096 worlds

Each seed-1/seed-2 run has 200 warmup, 1,000 measured environment steps and 40
profile steps. The 1,000-step span includes repeated episode resets. All runs
below have zero measured FPGS row drops/overflow and finite boundary states.

| Control | RTX maximum dense rows | GB300 maximum dense rows | Maximum global contacts, RTX / GB300 |
| --- | ---: | ---: | ---: |
| 640 rows, default contact pool, seed 0 (short control) | 598 | 602 | 114,109 / 115,735 |
| 640 rows, 196,608 global contacts, seed 1 | 609 | 624 | 115,666 / 114,713 |
| 704 rows, 147,456 global contacts, seed 2 | 602 | 599 | 115,972 / 116,990 |

The 704-row setting retains 12.8% above the largest observed 624-row demand.
The 147,456-slot contact pool retains roughly 25% above the earlier 118,209
contact peak, while removing 99.54% of the old 31,764,480 contact slots. The
known contact-plus-routing payload reduction is about 3.53 GiB; this is **not**
net process VRAM saving because row storage also increased.

The last run uses the new sticky checker and records all 4,960 collision calls
on each GPU: every observed collision queue has zero overflow. It still reveals
oversized intermediate queues: 14,864,384 broad-phase output slots versus
44,984 maximum observed demand, with similarly oversized GJK/work/query arrays.

`CollisionPipeline(..., broad_phase_output_max=N)` now permits an explicit
output bound without truncating the full immutable input pair list. Dependent
narrow-phase storage follows that bound. Defaults are unchanged; unsupported
modes/prebuilt components are rejected. Rightsizing can also change effective
split/sparse dispatch, so it must be revalidated rather than described as a
storage-only change. A 65,536-slot Keyboard control is pending GPU validation.
The unchanged Lab config rejects unknown Hydra keys: this new constructor
option must not be passed as an untested `+env...` override.

## MJWarp: two different issues

### Line search

3.12.0 exposes exhaustion that was previously silent; the corresponding
3.11-to-3.12 solver arithmetic was unchanged. The warning prints the current
15-iteration setting, not a calculated recommendation to raise it. Downgrading
or suppressing warnings would not fix the search.

A stock Kuka 64-world control records 688 / 653 affected world-solves (RTX /
GB300) out of 7,168. Outer iterations peak at 7 of 100 and no contact/row
capacity overflows occur. Disabling incremental reuse gives 651 / 655, ruling
out cached-gradient reuse as the main cause.

Captured rays identify an exact-zero derivative handling bug: `_in_bracket`
rejects a trial with derivative exactly zero. A saved GB300 ray exhausts 15
iterations in literal FP32 replay; zero-inclusive bracket and convergence tests
accept its exact stationary point in one iteration. A native CPU kernel
regression also demonstrates that the old code can discard that point and
return a nonstationary bracket endpoint.

A diagnostic helper-only correction reduces the paired Kuka failures to
27 / 35, with unchanged iteration limits and no capacity/nonfinite failures.
That partial correction still misses convergence if zero is first accepted on
the final allowed iteration. Full correction and remaining-ray investigation
are ongoing. Warning-free execution alone will not establish physical
convergence: independent stored-force balance is being checked too.

Friction absolute-cost cancellation is separately reproducible, but must not
be conflated with the proven zero-bracket bug. It has not been promoted into
the runtime.

### Capacity initialization

Keyboard 4K, stock MJWarp, seed 0, 200 warmup + 200 environment + 40 profile
steps: requested `njmax=384`, `nconmax=36` and 147,456 Newton contact slots.
Measured row demand peaks at **272** on each GPU and pooled contacts at
**103,551 / 103,443**. No observed capacity overflow occurs, but line-search
failures remain: **1,463,063 / 1,463,595** world-solves.

The requested contact reservation does not take effect: CPU initialization
produces 120 native contacts, then the adapter raises `nconmax` to 120 and
allocates **491,520** pooled/ Newton contacts. External collision is used in
this task. A consistent external-collision initialization fix is under study;
merely overwriting `ncon` would leave inconsistent CPU constraint state and
is not acceptable.

`njmax` is per-world; `nconmax` is a pooled reservation multiplied by world
count. Never confuse pooled average reservation with a hard per-world limit.
Do not shrink sparse Jacobian storage independently without measuring its
unclamped transient demand.
