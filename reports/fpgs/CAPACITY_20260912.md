It is correctness and capacity work, **not an optimization speedup claim**. Previous
Keyboard timings with dropped rows and MJWarp timings with line-search warnings
are not an accuracy-fair baseline.

## FPGS: missing rows were real

Keyboard's old 192-row dense allocation could see **615 requested rows** and
drop **423**. These are mostly three-row frictional contacts, not duplicated
keyboard position limits. The 108 independent keyboard key limits use the
existing fused path outside this allocator.

The implementation now latches dense, matrix-free, propagation, and incoming
contact-capacity failures independently of opt-in detailed telemetry. Four
int32 flags survive successful/empty steps and CUDA graph replays. They add no
new per-step kernel or host synchronization. `constraint_capacity_status()`
reads them; `check_constraint_capacity()` raises. Call at safe host observation
boundaries on the correct/joined stream. Explicit clearing acknowledges an
earlier failure; it cannot repair lost work. This is not automatic graph abort.

This API does **not** cover upstream collision queues or the separate matrix-free
unique-body cap. `NarrowPhase.buffer_capacity_status()` and
`check_buffer_capacity()` now separately retain all 13 existing narrow-phase
verification conditions in a four-byte word, using the existing verifier kernel.
Keep `verify_buffers=True` throughout. These flags do not cover soft/hydroelastic
internal storage or post-narrow owners such as body-pair reduction/contact
matching. A hash-load warning is not itself proof of lost contacts. Neither
boolean API estimates required capacity; measure unclamped demand separately.

Regression-first tests include 205 sphere-plane contacts: 640- and 768-row
solutions agree within FP32 tolerance and satisfy physical checks; 192 rows
omit a necessary contact and change motion. The initial combined **68 tests passed
on both GPUs with no skips**, including sticky row/collision status during graph
replay, compact collision storage and MJ initialization; the later response
correction expands this to 83 tests. Three broader
CPU-path failures were reproduced on the clean starting revision and are not
claimed fixed by this change.

## MJWarp: two different issues

### Line search

3.12.0 exposes exhaustion that was previously silent; the corresponding
3.11-to-3.12 solver arithmetic was unchanged. The warning prints the current
15-iteration setting, not a calculated recommendation to raise it. Downgrading
or suppressing warnings would not fix the search.

A stock Kuka 64-world control records 688 / 653 affected world-solves (RTX /
GB300) out of 7,168. Outer iterations peak at 7 of 100 and no contact/row
capacity overflows occur. Disabling incremental reuse gives 651 / 655, ruling
out cached-gradient reuse as the main cause.

Captured rays identify an exact-zero derivative handling bug: `_in_bracket`
rejects a trial with derivative exactly zero. A saved GB300 ray exhausts 15
iterations in literal FP32 replay; zero-inclusive bracket and convergence tests
accept its exact stationary point in one iteration. A native CPU kernel
regression also demonstrates that the old code can discard that point and
return a nonstationary bracket endpoint.

At an earlier diagnostic stage, the helper-only correction reduced Kuka failures to
27 / 35, with unchanged iteration limits and no capacity/nonfinite failures.
That partial correction still misses convergence if zero is first accepted on
the final allowed iteration. A second cause is an unattainable derivative
threshold on the FP32 alpha grid. A captured Keyboard ray has curvature around
210: one alpha ULP changes its derivative by about 2.5e-5, while the threshold
is 1.85e-6. FP64 accumulation alone cannot make an unrepresentable alpha exist.

A diagnostic correction accepts exact stationary trials, breaks exact cost
ties by stationarity, preserves geometric progress inside a finite sign
bracket, and recognizes adjacent representable bracket endpoints. Existing
evaluation and iteration budgets are unchanged; genuine budget exhaustion
still raises the warning. Small 64-world controls, 7,168 world-solves each:

| Task | Stock line-search failures, RTX / GB300 | Corrected failures, RTX / GB300 |
| --- | ---: | ---: |
| Kuka | 688 / 653 | 0 / 0 |
| Keyboard | Stock 64-world count not captured | 0 / 0 |
| Franka | 157 / 157 | 3 / 3 |

Keyboard's earlier full-zero-only control has 195 / 189 failures. Franka's
remaining rays stalled before obtaining a sign bracket when a Newton proposal
rounded back to its endpoint; the final correction is described below. Independent
stored-force balance is finite throughout these controls, but is not an
independent constitutive-law or whole-trajectory accuracy proof. Large active
Keyboard contact forces are being traced to their actual owning rows rather
than dismissed as inactive storage.

Friction absolute-cost cancellation is separately reproducible, but must not
be conflated with the proven zero-bracket bug. It has not been promoted into
the runtime.

Measured row demand peaks at **272** on each GPU and pooled contacts at
**103,551 / 103,443**. No observed capacity overflow occurs, but line-search

The requested contact reservation does not take effect: CPU initialization

allocates **491,520** pooled/ Newton contacts. External collision is used in

existing CPU forward call only for the external-collision GPU seed, restoring
the exact option flags in `finally` before device transfer. Noncontact seed
constraints remain consistent; native/CPU paths and later GPU warm-start policy
are unchanged. Seven focused initialization tests pass. A 64-world GPU smoke
test and held-out seed-1 4K run both honor the requested capacities exactly,
with CPU seed `ncon=0`, `nefc=6`.

All 4,960 collision calls per GPU have zero raw queue overflow; all 13 sticky
narrow flags and all MJ capacity bits remain clear. Reserves above the largest

observed capacity safety through these held-out resets, not a universal bound.
Reachable unique Warp backing storage is 1,430,956,127 bytes per device; this
is not process VRAM. The old 491,520-contact seed-driven allocation is no

That earlier run is **not accepted as warning-free timing**: its adjacent-float search
still has 38 / 34 line-search failures across 40,632,320 world-solves per GPU.
There are no outer iteration exhaustions or nonfinite solves. Independently
recomputed stored-force balance is finite/in-bounds on every observed solve.
The first remaining rays again lack a sign bracket. Unlike Franka's exact
roundback, their Newton trials move by one/four ULPs; endpoint insertion and
rounded-gradient plateaus are being investigated. They remain part of the next
correction's tests; a roundback-only fix is not yet sufficient evidence.

A captured huge active force belongs to ground versus the fixed Keyboard case,
with exactly zero Jacobian, zero response weight and `D` near 1e15. Its large
force contributes no generalized force. This proves the captured row's owner,
not that every large force is harmless. FPGS already filters nonresponsive
endpoints before allocating solver rows, so this MJ row does not explain the
FPGS 624-row high-water mark.

The external-conversion filter was incomplete: Newton exports some articulated
fixed/locked-D6 roots as mocap bodies with nonzero MuJoCo weld IDs. Testing only
`body_weldid == 0` missed them. The adapter now uses native MuJoCo's welded
ancestor DOF count, retaining a contact whenever either endpoint can respond
(and preserving the existing explicit-kinematic rule). A fixed child on a
dynamic parent remains responsive; using the leaf body's DOF count would be
incorrect. No force-magnitude/inverse-weight threshold is used, and native MJ
collision is unchanged. This removes spurious public contact forces, not
capacity-driven loss of physically responsive contacts.

Regression-first tests failed before the correction. The full **83-test suite
passes on each GPU without skips**, including real sparse solves/force
publication, repeated cached conversion, invalidation, empty/refill transitions
and CUDA graph replay. Full pre-commit passes.

### Deeper line-search acceptance regressions

Further diagnosis found a missing-sign acquisition bug: both same-sign
endpoints reject a trial across the minimum. The old no-progress termination
can therefore report convergence at a substantially incorrect point with no
warning. An actual native CPU convex two-contact example stops at `x=0.49`
instead of `1.3`, with gradient magnitude `3.51` and objective regret `2.11005`.
Its physical Newton direction and SPD smooth mass are consistent, not synthetic
warning inputs. The mirrored objective reproduces the same failure.

The diagnostic correction acquires the missing-sign endpoint from the existing
three evaluated trials, then refines the bracket. A second three-contact
counterexample requires accepting collapsed same-sign anchors (`lo_alpha ==
hi_alpha`); a strict ordering precondition otherwise falsely converges at
`1.3` instead of `2.2`. Both corrected mirrored CPU examples reach their exact
minima within FP32 accuracy using the unchanged 15-iteration budget.
Warning-free alone is demonstrably not a sufficient numerical acceptance
criterion.

The final combined correction passes Franka64 on both GPUs with **zero**
line-search/outer/capacity failures (old stock157, partial fixes3 per GPU).
The full held-out Keyboard4K seed-1 run repeats the 200/1,000/40 sampling and
all-call observers, retaining `njmax=320`, `nconmax=32`, 131,072 Newton contacts
and 45,056 broad-output slots:

iterations. Separate traced controls use 16,384 worlds, seed 0, 200 warmup /

| ANYmal-D | 1 / 2 | 0 / 0 |

All four paired controls have zero observed outer, row/contact-capacity and
nonfinite failures. This does **not** qualify the corrected elliptic path for
promotion. The exact failure rays expose different numerical issues:

- Allegro: on both stock rays, large frictionloss absolute costs swamp a small
  true improvement. Independent raw FP64 initial-step cost changes are
  -6.448e-6 / -2.868e-6; the GPU reports +3.419e-6 / +1.154e-5 instead. Replacing
  only frictionloss shifted-cost evaluation in CPU replay restores negative
  cost changes with unchanged derivatives. Actual GPU validation is pending.
- ANYmal-D: there are no frictionloss rows. Near-cancellation in the prepared
  tangent-norm quadratic and its evaluation shifts the derivative root. Both
  raw-input FP64 roots and high-precision roots of the stored coefficients lie
  outside the saved GPU derivative-sign brackets. The FP32 alpha grid also
  cannot attain the nominal derivative threshold. Clearing the warning with
  adjacent-bracket termination does not independently repair the evaluator.

The production opt-in helper therefore remains pyramidal-only. Neither cone
switching nor relaxed tolerances are used to make these controls pass. Stable
evaluation and explicit numerical acceptance remain work in progress.

## Reproduction entrypoint

The retained `manifest.json` in each evidence directory contains exact paired
diagnostic commands, source pins and hardware UUIDs. Diagnostic captures are
not timing samples. For an actual checked Keyboard4K comparison, use the
Newton-owned driver below with the existing Lab checkout; choose a fresh
output directory. The driver uses seed0, while the held-out calibration above
uses seed1. It rechecks all supported sticky flags and refuses affected results.

```sh
uv run --no-project --python /path/to/isaaclab/.venv/bin/python \
  python tools/fpgs_bench/compare_backends.py \
  --isaaclab /path/to/isaaclab --fpgs /path/to/newton --mjwarp /path/to/newton \
  --gpus 0 1 --task keyboard-so101 --num-envs 4096 \
  --warmup-steps 200 --steps 1000 --profile-steps 40 --repeats 3 \
  --check-overflow --mjwarp-linesearch-fix \
  --capacity keyboard-so101:fpgs:dense_max_constraints=704 \
  --capacity keyboard-so101:fpgs:rigid_contact_max=147456 \
  --capacity keyboard-so101:fpgs:broad_phase_output_max=57344 \
  --capacity keyboard-so101:mjwarp:njmax=320 \
  --capacity keyboard-so101:mjwarp:nconmax=32 \
  --capacity keyboard-so101:mjwarp:rigid_contact_max=131072 \
  --capacity keyboard-so101:mjwarp:broad_phase_output_max=45056 \
  --output-dir /path/outside/checkouts/keyboard-checked
```

The example is scoped to the supported pyramidal Newton task. Do not change
Allegro/ANYmal-D's elliptic cone to make it fit this workaround.

`njmax` is per-world; `nconmax` is a pooled reservation multiplied by world
count. Never confuse pooled average reservation with a hard per-world limit.
Do not shrink sparse Jacobian storage independently without measuring its
unclamped transient demand.
