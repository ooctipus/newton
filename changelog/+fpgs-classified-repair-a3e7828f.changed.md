Repair `SolverFeatherPGS`'s cached dynamics on CUDA over a list of the cache groups that need it, built by a one-thread-per-group classification, when the repair would launch more blocks than about two waves, instead of launching one block per group that mostly confirms its cache: for the first repair of a CUDA graph capture, whose replays can follow any state, and eagerly when the step reads the state its caches were published into or a copy of it. Solvers with `enable_joint_velocity_limits=True` keep one block per group: their repair runs on every step, so a classification would add a launch to each step. Each listed group computes the same values as before. Set `FEATHER_PGS_TREE_REPAIR_CLASSIFY=0` to keep one block per group; `get_path_selection()["routes"]["held_tree"]["groups"][i]["classify_first"]` reports the choice, `["captured_repairs"]` how each repair of the latest capture was launched, and `["kernels"]` names the comparison, classification and listed repair kernels.
