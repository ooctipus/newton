Add an experimental opt-in `FEATHER_PGS_PATCH_CONDITIONAL_NODES=1` that sorts the patch-friction contact pairs of `SolverFeatherPGS` under a conditional CUDA graph node: captured graphs then skip the sort for empty contact frames and on steps that receive the contact frame sorted last (the same `Contacts`, `contact_generation` and contact count), which is every second substep of a collision pass in two-substep setups. It is opt-in because four of 21 Isaac Lab tasks ran slower per step with it (Kuka lift +3.8%, Kuka reorient +3.3%, an SO-101 keyboard task +1.2% and Ant +1.8%), while the other 17 were unchanged or up to 27% faster. It is experimental because memory checkers report errors on the conditional-node path alone that remain unexplained: Nsight Systems node-level graph tracing fails with an illegal memory access on the Kuka and Ant tasks, and compute-sanitizer reports invalid reads in the pair sort inside the node. Set `FEATHER_PGS_PATCH_CONDITIONAL_NODES=1` before constructing the solver to enable it; unset, `0` or any other value keeps the sort unconditional, and `get_path_selection()["routes"]["friction"]["conditional_nodes"]` records the choice and its reason. With the node, code that rewrites contact arrays between captured steps without a collision pass must advance `contact_generation` (for example with `Contacts.clear()`) or change the count, and the node pauses the capture once per step, so an event recorded before `step()` cannot be waited on after it; a step taken while a stream forked by the caller still holds unjoined work sorts unconditionally.
